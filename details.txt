4. ARCHITECTURE & ADAPTER CONTRACT V1 SPECIFICATION
================================================================================
The official adapter specification is codified in `docs/adapter-v1.md`. It defines
the binary and IPC contract that all competing team repositories must satisfy.

4.1 Process Model and Execution Lifecycle
-----------------------------------------
- The judging harness starts a brand-new operating system process for EVERY
  SINGLE OPERATION request.
- Exactly one supported entrypoint must exist at the ROOT of the team's repository:
    * `track4_service.py` (Python)
    * `track4_service.cjs` (CommonJS Node.js)
    * `track4_service.js` (JavaScript Node.js)
    * `track4_service.mjs` (ES Module Node.js)
- The process is executed with the current working directory set to the root of
  the submission repository.
- Because a new process is spawned for each request, in-memory state does NOT
  persist across calls. Teams MUST serialize and persist application state,
  access policies, active keys, and audit logs to the file system before exiting.

4.2 I/O Protocol and Stream Handling Rules
------------------------------------------
- Standard Input (stdin):
  The process reads exactly one UTF-8 encoded JSON object from standard input
  until end-of-file (EOF).
- Standard Output (stdout):
  The process must emit exactly ONE JSON object to standard output, followed by
  a newline, and terminate with exit code 0.
- Standard Error (stderr):
  Diagnostics, error details, and debug traces must be written exclusively to
  stderr.
- Stream Size Limits:
  Neither stdout nor stderr may exceed 64 KiB (65,536 bytes) per request.
  Exceeding this buffer causes immediate validation failure.
- Absolute Secrecy Rule:
  Stdout and stderr MUST NEVER contain private keys, symmetric secrets, KEM shared
  secrets, synthetic sensitive values (`key_material`), or protected data bodies
  during denied access. Leakage triggers immediate test failure.
- Identifier Rule:
  All identifiers (`actor`, `asset`, `request_id`, `challenge`) must be treated
  as opaque, case-sensitive strings.

4.3 Judging Runtime & Sandboxed Environment Constraints
-------------------------------------------------------
- Evaluation takes place in an offline, network-isolated Linux container.
- Base System: Linux container with read-only root filesystem.
- Runtimes Installed:
    * Python 3.12 (standard library)
    * Node.js 24.11.1
    * Post-Quantum Crypto Library: `pqcrypto==0.4.0` (Python)
- Dependency Policy:
  The judging worker does NOT run package managers (`pip install` or `npm install`)
  during test runs. Only pre-installed system packages and libraries checked
  directly into the team repository may be used.
- File System Persistence:
  Because the root filesystem is read-only, all persistent files MUST be written
  to a designated writable temporary directory.
  The judging harness injects environment variables:
    * `TRACK4_STATE_DIR` (Primary target set by local validator)
    * `TMPDIR`, `TEMP`, `TMP` (Standard POSIX/Windows temp fallback variables)
  When `TRACK4_STATE_DIR` is set, teams must store state inside it. Otherwise,
  they must fall back to the operating system temporary directory.
  A fresh container starts with an empty state directory.

4.4 Full API Operation Specifications
--------------------------------------
The contract mandates five core operations identified by the `"op"` field:

1. Operation: `setup`
   - Purpose: Cleanly initialize or reset the application's state, permissions,
     and resources.
   - Request JSON Fields:
       * `op`: "setup" (string)
       * `owners`: Object mapping asset ID string -> actor ID string.
         Example: `{"brief": "maya", "doc-99": "carol"}`
       * `contents`: Object mapping asset ID string -> string body.
         Example: `{"brief": "demo note", "doc-99": "confidential text"}`
       * `disabled`: Array of actor ID strings whose accounts are revoked.
         Example: `["eve", "malicious_user"]`
       * `key_material`: Synthetic sensitive string representing root secret material.
         Example: `"38f9a2b7c4d1..."`
   - Required Response:
       `{"ready": true}`
   - Behavioral Requirements:
       * Wipe any pre-existing state in the state directory.
       * Commit the initial owners, contents, and disabled status to disk.
       * The `key_material` must be stored securely or utilized internally; it
         must NEVER be echoed to stdout or stderr.

2. Operation: `read`
   - Purpose: Retrieve the stored plaintext body of a protected asset.
   - Request JSON Fields:
       * `op`: "read" (string)
       * `actor`: Actor ID attempting access (string)
       * `asset`: Asset ID being requested (string)
       * `request_id`: Unique tracking identifier for this read invocation (string)
   - Permitted Responses:
       * If Authorized (actor owns asset and is NOT disabled):
         `{"decision": "allow", "body": "<exact stored string body>"}`
       * If Denied (wrong owner, unknown asset, or disabled actor):
         `{"decision": "deny"}`
   - Behavioral Requirements:
       * Strict Content Protection: When `decision` is "deny", the response
         MUST NOT contain a `body` field or disclose any protected value.
       * Nonce Audit Correlation: The system must persist an immutable audit
         record binding `request_id` to the final `decision`.

3. Operation: `revoke`
   - Purpose: Revoke an actor's access credentials immediately across the service.
   - Request JSON Fields:
       * `op`: "revoke" (string)
       * `actor`: Actor ID to be revoked (string)
   - Required Response:
       A JSON object, typically `{}`.
   - Behavioral Requirements:
       * Add the actor to the disabled registry and commit to disk.
       * Subsequent read operations by this actor must return `decision: "deny"`.
       * Revocation of one actor must NOT impair or affect any other actor's
         authorized access.

4. Operation: `audit`
   - Purpose: Query the recorded outcome of a previous access request by its ID.
   - Request JSON Fields:
       * `op`: "audit" (string)
       * `request_id`: Unique request tracking identifier to look up (string)
   - Required Response:
       `{"request_id": "<request_id>", "decision": "allow" | "deny"}`
   - Behavioral Requirements:
       * The returned `request_id` and `decision` must strictly match the
         actual outcome enforced during the original `read` operation.

5. Operation: `protected_read`
   - Purpose: Perform authenticated, post-quantum encrypted access to an asset.
   - Request JSON Fields:
       * `op`: "protected_read" (string)
       * `actor`: Actor ID attempting access (string)
       * `asset`: Asset ID being requested (string)
       * `challenge`: Fresh random nonce string generated by the caller (string)
       * `public_key`: Standard Base64-encoded raw ML-KEM-768 public key (string)
   - Authorized Response:
       `{"ciphertext": "<base64_kem_ciphertext>", "proof": "<hex_hmac_sha256>"}`
   - Behavioral Requirements:
       * Enforce standard authorization (verify actor ownership and non-disabled state).
       * If denied, return `{"decision": "deny"}` without ciphertext or proof.
       * If authorized, execute ML-KEM-768 encapsulation against `public_key`.
       * Produce a 32-byte shared secret `ss` and KEM ciphertext `ct`.
       * Return `ct` encoded in standard Base64 in `"ciphertext"`.
       * Compute HMAC-SHA-256 using `ss` as the cryptographic key over:
           `payload = (challenge + stored_body).encode("utf-8")`
         (Exact binary concatenation of challenge and body, NO separator).
       * Return the resulting HMAC digest as a lowercase hexadecimal string in `"proof"`.
       * The shared secret `ss` must remain strictly isolated in RAM and erased.

4.5 Post-Quantum Cryptography (ML-KEM-768) Details
--------------------------------------------------
- Algorithm: ML-KEM-768 (standardized under NIST FIPS 203, formerly Kyber-768).
- Key Format: Raw bytes of the public key (1184 bytes for ML-KEM-768), standard Base64.
- Ciphertext Format: Raw bytes of the encapsulation ciphertext (1088 bytes), standard Base64.
- Shared Secret: 32 bytes (256 bits).
- HMAC Calculation:
    HMAC-SHA-256(Key = shared_secret, Msg = UTF-8(challenge + stored_body))
- The judging harness uses `pqcrypto==0.4.0` in Python (`pqcrypto.kem.kyber768`).

4.6 Root-Level threat-model.json Schema

If a team's implementation conforms to the standard lost-device scenario, the
official worker automatically checks for the existence of `threat-model.json`
at the repository root:

5. THE 12 CORE CHALLENGE OBJECTIVES & EVIDENCE REQUIREMENTS
================================================================================
The official Track 4 problem statement and `templates/evidence-sheet.md` define
12 core security goals. Teams must address these in their system design, codebase,
and evidence sheet.

--------------------------------------------------------------------------------
Goal 1: Key Rotation
--------------------------------------------------------------------------------
- Description: Active cryptographic keys must be rotated without service downtime.
- Requirements:
    * Authorized file/message transfers must continue uninterrupted during rotation.
    * Every node must reject new requests that use the old key after the cutoff.
    * Teams must document whether an overlap grace period applies.
    * Version IDs, activation timestamps, and operational metrics must be recorded.
    * Secret key values must never be exposed in logs or test outputs.

--------------------------------------------------------------------------------
Goal 2: Revocation Across Nodes
--------------------------------------------------------------------------------
- Description: When an identity or device is revoked, all nodes must enforce it.
- Requirements:
    * Measure propagation delay: the exact time between revocation initiation
      and the instant the last distributed node enforces denial.
    * After device loss, the legitimate owner can re-enroll securely.
    * Unaffected peers must maintain continuous, uninterrupted access.
    * Evidence must record node-specific decisions and clock uncertainty.

--------------------------------------------------------------------------------
Goal 3: Crash Recovery
--------------------------------------------------------------------------------
- Description: Resilience against abrupt power failure or process termination.
- Requirements:
    * After an interrupted key rotation or crash, the service recovers a
      consistent, authorized state upon restart.
    * Previously revoked keys must remain revoked (no resurrection vulnerability).
    * Committed keys and protected assets must remain accessible.
    * Restart time and read-after-crash behavior must be measured.

--------------------------------------------------------------------------------
Goal 4: Backup Integrity
--------------------------------------------------------------------------------
- Description: Key and state backups must be tamper-evident and recoverable.
- Requirements:
    * Recovery procedures must detect corrupted or maliciously altered key backups.
    * The service must abort restoration and refuse to use corrupted keys.
    * Only authenticated, verified key backups may be restored.
    * Evidence records backup ID, content digest (SHA-256), and restore status.

--------------------------------------------------------------------------------
Goal 5: Log Integrity
--------------------------------------------------------------------------------
- Description: Audit logs must resist tampering, injection, and evasion.
- Requirements:
    * Each event must immutably preserve original identity, action, and boundary.
    * User-supplied text (e.g. carriage returns, newlines, JSON brackets) must
      not create phantom log entries or overwrite the recorded actor.
    * Operators must be able to cryptographically verify log integrity (e.g. via
      hash chains, Merkle trees, or digital signatures).

--------------------------------------------------------------------------------
Goal 6: Routine and Suspicious Activity
--------------------------------------------------------------------------------
- Description: Telemetry anomaly detection distinguishing benign from malicious actions.
- Requirements:
    * Use context (such as change tickets and approvals) to differentiate routine
      administration from unauthorized privilege escalation or data exfiltration.
    * Performance metrics on labelled datasets must report:
        - F1 Score
        - Median time to alert
        - False alerts per 1,000 benign events
    * The system must correctly identify approved role changes vs rogue changes.

--------------------------------------------------------------------------------
Goal 7: Lateral Movement
--------------------------------------------------------------------------------
- Description: Detection of unusual cross-service communication hops.
- Requirements:
    * The detector must flag atypical access paths between services even when
      the caller presents valid credentials.
    * Correlation: group events by actor, session, correlation ID, and flow.
    * Distinct alerts must identify the suspicious service edge sequence and
      distinguish denied requests from successful unauthorized access.

--------------------------------------------------------------------------------
Goal 8: Clock Differences
--------------------------------------------------------------------------------
- Description: Robustness against distributed clock skew and out-of-order logs.
- Requirements:
    * The system must ingest events with variable network delays and clock offsets.
    * Timestamps must be preserved: raw event time, received time, and offset.
    * Corrected event time = event_time - source_clock_offset.
    * State the supported timing uncertainty window; flag ambiguous sequences.

--------------------------------------------------------------------------------
Goal 9: Replay and Recipient Binding
--------------------------------------------------------------------------------
- Description: Protection against message replay and recipient redirection.
- Requirements:
    * End-to-end encrypted messages must be cryptographically bound to the
      intended recipient identity.
    * The receiver must reject duplicate messages (nonce/timestamp tracking).
    * The receiver must reject messages if recipient metadata was altered in transit.

--------------------------------------------------------------------------------
Goal 10: Forward Secrecy
--------------------------------------------------------------------------------
- Description: Future key compromise must not compromise past session confidentiality.
- Requirements:
    * Compromise of long-term identity keys must not reveal historical session traffic.
    * Session keys must be ephemeral and securely erased (zeroized) after use.
    * Specify cryptographic primitives (e.g. ephemeral KEM or ratcheting).

--------------------------------------------------------------------------------
Goal 11: Delivery Under Loss or Reordering
--------------------------------------------------------------------------------
- Description: Protocol resilience over unreliable network transport.
- Requirements:
    * The system must handle message loss, delayed packet arrival, and reordering.
    * Reassembly must ensure that only complete, authenticated messages are delivered.
    * Incomplete or corrupted packets must be safely discarded with logged errors.

--------------------------------------------------------------------------------
Goal 12: Session Resumption (if supported)
--------------------------------------------------------------------------------
- Description: Secure session resumption without impersonation vulnerabilities.
- Requirements:
    * Resumed sessions must remain cryptographically bound to the original peer.
    * An adversary presenting a stolen session ID must be rejected.
    * Fresh policy checks must execute upon resumption; if not supported, mark
      status as `not supported`.

6. LOCAL VALIDATION ENGINE INTERNALS (validate.py)
================================================================================
`validate.py` is the official conformance checker. It exercises a team's adapter
against the lost-device scenario. It comprises 199 lines of pure standard-library
Python code, requiring no third-party dependencies.

6.1 Architecture, Threading, and Stream Draining
------------------------------------------------
The core execution engine is encapsulated in the `execute()` function:
```python
def execute(command, request, directory, timeout, cwd=None):
```
Execution Lifecycle Details:
1. Environment Configuration:
   A cloned environment dictionary is prepared. Four environment variables are
   explicitly pointed to the temporary test directory:
     `TRACK4_STATE_DIR = str(directory)`
     `TMPDIR = str(directory)`
     `TEMP = str(directory)`
     `TMP = str(directory)`
2. Subprocess Launch:
   `subprocess.Popen(command, cwd=cwd, env=env, stdin=PIPE, stdout=PIPE, stderr=PIPE)`
   If execution fails at the OS level (e.g. file not found or permission denied),
   it raises `ValidationError("setup", "Cannot start adapter. Check runtime and entry path.")`.
3. Dedicated Stream Draining (Anti-Deadlock Mechanism):
   To prevent pipe deadlocks and runaway buffer bloat, two daemon threads are
   spawned to drain `stdout` and `stderr` in chunks of 8192 bytes:
   ```python
   def drain(stream, target):
       with stream:
           while chunk := stream.read(8192):
               target.extend(chunk[:max(0, 65537 - len(target))])
   ```
   Each buffer retains at most 65,537 bytes (64 KiB + 1 byte overflow canary).
4. Asynchronous Stdin Feeding:
   A third thread feeds the JSON request payload encoded as UTF-8 into `process.stdin`.
5. Timeout Enforcement:
   `process.wait(timeout=timeout)` enforces a strict wall-clock timeout (default 8s).
   If expired, `process.kill()` terminates the process and raises:
   `ValidationError("setup", "Adapter exceeded per-operation timeout.")`.
6. Stream Termination & Thread Join:
   All three threads are joined with a 200ms grace period (`thread.join(0.2)`).
   If any thread remains alive (e.g. because a spawned child process holds the pipe
   open), it raises:
   `ValidationError("setup", "Adapter left output streams open. Stop background child processes.")`.
7. Stream Size Verification:
   If `len(buffer) > 65536`, it raises:
   `ValidationError("format", "Adapter output exceeded 64 KiB per stream.")`.
8. Return Code Verification:
   If `process.returncode != 0`, it raises:
   `ValidationError("setup", "Adapter exited unsuccessfully. Check dependencies and local state handling.")`.

6.2 Security Boundaries and Secret Leak Detection
-------------------------------------------------
The validator injects random cryptographic tokens into each test run:
  - `actor`, `peer`, `disabled`: 16-byte random hex tokens (`secrets.token_hex(16)`).
  - `asset`, `other`: 12-byte random hex tokens (`secrets.token_hex(12)`).
  - `body`, `peer_body`, `marker`: 24-byte random hex tokens (`secrets.token_hex(24)`).
  - `marker` is passed as `key_material` during `setup`.

Leak Detection Rules:
1. Marker Presence in Streams:
   If `marker.encode()` is detected anywhere in the raw `stdout` or `stderr` streams,
   the internal flag `leaked` is set to `True`.
2. Content Disclosure on Denial:
   The helper `contains_protected_value(response)` scans serialized JSON responses:
   ```python
   def contains_protected_value(response):
       encoded = json.dumps(response, ensure_ascii=False)
       return any(value in encoded for value in (body, peer_body, marker))
   ```
   If an adapter returns `decision: "deny"`, but the response contains any of `body`,
   `peer_body`, or `marker`, or contains a non-empty `body` field, it records a
   behavior failure for unauthorized data disclosure.

6.3 Step-by-Step Test Execution Flow (12 Verification Steps)
------------------------------------------------------------
The `validate()` function executes a sequence of 12 checks across two clean
temporary directories:

Directory 1 (Main Lost-Device Scenario):
  1. `clean setup`:
     - Invokes `op="setup"` with `actor` owning `asset` (`body`), `peer` owning
       `other` (`peer_body`), `disabled=[disabled]`, and `key_material=marker`.
     - Asserts response `ready == True`.
  2. `owner before device loss`:
     - Invokes `op="read"`, `actor=actor`, `asset=asset`.
     - Asserts `decision == "allow"` and `body == body`.
  3. `peer before device loss`:
     - Invokes `op="read"`, `actor=peer`, `asset=other`.
     - Asserts `decision == "allow"` and `body == peer_body`.
  4. `wrong owner`:
     - Invokes `op="read"`, `actor=actor`, `asset=other` (actor requesting peer's asset).
     - Asserts `decision == "deny"` and body is omitted/empty.
  5. `revoke lost-device owner`:
     - Invokes `op="revoke"`, `actor=actor`.
     - Asserts successful response object returned.
  6. `owner after revocation`:
     - Invokes `op="read"`, `actor=actor`, `asset=asset` using fresh `request_id`.
     - Asserts `decision == "deny"` and body is omitted/empty.
  7. `audit revoked read`:
     - Invokes `op="audit"`, `request_id=request_id` (from Step 6).
     - Asserts `audit["request_id"] == request_id` and `audit["decision"] == "deny"`.
  8. `unaffected peer`:
     - Invokes `op="read"`, `actor=peer`, `asset=other`.
     - Asserts peer still receives `decision == "allow"` and exact `peer_body`.
  9. `revocation persists across processes`:
     - Invokes `op="read"`, `actor=actor`, `asset=asset` in a brand-new process.
     - Asserts `decision == "deny"` persists from disk.

Directory 2 (Fresh Rerun Verification):
  10. `fresh rerun setup`:
      - Runs setup in a second clean temporary directory with the same initial data.
      - Asserts response `ready == True`.
  11. `fresh rerun owner`:
      - Runs read for `actor` on `asset`.
      - Asserts `decision == "allow"` and exact `body`. Demonstrates that previous
        revocation was scoped to the previous directory and does not bleed over.

Global Leak Check:
  12. `fake key stays out of output`:
      - Asserts that `leaked` is `False`. Confirms synthetic `key_material` was never
        emitted to stdout or stderr across all invocations.

6.4 Diagnostic Reporting and Exit Code Specification
----------------------------------------------------
Each check records a structured dictionary:
`dict(category=category, name=name, passed=bool(passed), detail=detail)`
where `category` is one of:
  - `"setup"`: Process launch, file missing, timeout, unhandled exit.
  - `"format"`: JSON syntax, stream size, required structure, decision values.
  - `"behavior"`: Authorization decisions, body correctness, leak prevention, audit.

Exit Code Rules (`exit_status(checks)`):
  - Return Code 0: All checks passed.
  - Return Code 1: Behavior failure (wrong decision, data leak, bad audit).
  - Return Code 2: Setup or execution failure (cannot start process, timeout, crash).
  - Return Code 3: Format failure (stdout not a JSON object, output > 64 KiB).
Precedence order: Setup errors (2) take priority over Format errors (3), which take
priority over Behavior errors (1).

6.5 CLI Parameters and Configuration
------------------------------------
Usage:
  `python validate.py --entry <path_to_adapter> [--timeout <seconds>]`
Flags:
  `--entry`: Path to adapter file (`.py`, `.js`, `.cjs`, `.mjs`). Required.
  `--timeout`: Maximum wall-clock seconds allowed per operation. Default: 8.0.

10.1 Python Demo (demo/python/team_app.py)
------------------------------------------
39 lines of implementation:
- State File: `Path(os.environ.get("TRACK4_STATE_DIR") or tempfile.gettempdir()) / "track4-practice-state.json"`
- Dispatch Logic:
    * `op == "setup"`:
      Stores `owners`, `contents`, `disabled`, and initializes `events = {}`.
      Returns `{"ready": True}`.
    * `op == "revoke"`:
      Appends `request["actor"]` to `state["disabled"]` if not present.
      Returns `{}`.
    * `op == "audit"`:
      Looks up `request["request_id"]` in `state["events"]`.
      Returns recorded event or `{"error": "unknown_request"}`.
    * `op == "read"`:
      Evaluates policy rules:
        - If `actor in state["disabled"]` -> `rule = "identity_disabled"`
        - If `asset not in state["owners"]` or `state["owners"][asset] != actor` -> `rule = "owner_required"`
        - Otherwise -> `rule = "owner_allowed"`
      Sets `decision = "allow"` if `rule == "owner_allowed"` else `"deny"`.
      If allowed, attaches `response["body"] = state["contents"][asset]`.
      Logs event to `state["events"][request_id]` with `request_id`, `decision`, and `rule`.
    * Other operations:
      Returns `{"error": "unsupported_operation"}` (specifically for `protected_read`).
- State is serialized via `STATE.write_text(json.dumps(state), encoding="utf-8")`.

11.4 Worked Analysis Scenarios & Case Studies (practice/examples.md)
--------------------------------------------------------------------
The documentation in `practice/examples.md` breaks down five crucial analysis
patterns that anomaly detectors must implement:

Scenario A: Approved Role Change (Events evt-003, evt-004, evt-005)
- Execution:
  `evt-003` records `user-admin` creating approval `change-100` on the `identity` service.
  `evt-004` shows `user-alex` transitioning from `viewer` to `report-reader`.
  `evt-005` records `user-alex` reading the `reports` service.
- Verification Logic:
  The detector correlates the event against `approvals.json`. The actor (`user-alex`),
  role (`report-reader`), time (`09:01:05Z`), and target service (`reports`) match
  `change-100` validity (`09:01:00Z` to `09:07:00Z`).
- Conclusion:
  The privilege escalation is approved and legitimate. Role elevation alone must
  not trigger a false positive alarm.

Scenario B: Unauthorized Privilege Escalation (Events evt-008, evt-009)
- Execution:
  `evt-007` records `user-blair` signing in as a `viewer`.
  `evt-008` records `user-blair` suddenly transitioning from `viewer` to `operator`
  with NO approval ID attached.
  `evt-009` shows `user-blair` reading the `reports` service using the newly gained role.
- Verification Logic:
  The detector searches `approvals.json` for an approval authorizing `user-blair` to
  assume the `operator` role. No record exists.
- Conclusion:
  Critical Alert: Flag as `unexpected_role_change` and `review_after_role_change`.
  Log both event IDs (`evt-008`, `evt-009`) and note missing change authorization.

Scenario C: Lateral Movement Sequence (Events evt-010, evt-011, evt-012)
- Execution:
  The service account `svc-report-worker` normally only calls `catalog` from `reports` (`evt-006`).
  In `flow-005` / `sess-worker`:
    * `evt-010`: calls `reports` -> `billing` (denied).
    * `evt-011`: calls `billing` -> `archive` (denied).
    * `evt-012`: calls `archive` -> `identity` to `list_roles` (denied).
- Verification Logic:
  All three service edges are completely unexpected for `svc-report-worker`.
  The requests share the same session (`sess-worker`) and correlation ID (`flow-005`).
- Conclusion:
  Candidate Lateral Movement Sequence. Group the three events into a single incident.
  Do NOT report successful breach or compromise, because all three requests were
  successfully blocked (`outcome: deny`).

Scenario D: Out-of-Order Ingestion vs Event Sequencing (Events evt-013, evt-014)
- Observation:
  In `events.csv`, line 14 is `evt-014` and line 15 is `evt-013`.
  `evt-014` has source timestamp `09:05:02.000Z` and arrived at `09:05:02.200Z`.
  `evt-013` has source timestamp `09:05:01.000Z` but arrived at `09:05:04.200Z`.
- Analysis:
  `evt-013` occurred BEFORE `evt-014`, but arrived 2 seconds LATER due to network delay.
- Required Handling:
  The pipeline must preserve both timestamps:
    - Receipt order (`evt-014` then `evt-013`) for ingestion and pipeline analysis.
    - Source event order (`evt-013` then `evt-014`) for behavioral timeline reconstruction.
  Do NOT mistake delayed arrival for a replay attack.

Scenario E: Source Clock Offset and Skew Compensation (Event evt-015)
- Observation:
  `evt-015` records `event_time_utc = 2026-01-15T09:06:03.000Z`, but
  `received_time_utc = 2026-01-15T09:06:01.200Z`, with `source_clock_offset_ms = 2000`.
- Mathematical Correction:
  `corrected_event_time = 09:06:03.000Z - 2000 ms = 09:06:01.000Z`.
  Actual delivery delay = `09:06:01.200Z - 09:06:01.000Z = 200 ms`.
- Conclusion:
  Without offset compensation, the event appears to have arrived 1.8 seconds BEFORE
  it occurred (an impossible negative latency). Compensating for clock offset resolves
  the anomaly and confirms a benign 200ms transit delay.

Scenario F: Multi-Node Revocation & Unaffected Scope (Events evt-016, evt-017, evt-018, evt-021)
- Execution:
  `evt-016` records `user-admin` revoking Alex's `report-reader` role under `change-101` at `09:07:00Z`.
  `evt-017` (at `09:07:02Z` on `reports-node-a`) denies Alex's read request.
  `evt-018` (at `09:07:03Z` on `reports-node-b`) denies Alex's read request.
  `evt-021` (at `09:09:00Z` on `catalog`) ALLOWS Alex's read request under the `viewer` role.
- Conclusion:
  Demonstrates proper distributed revocation enforcement: both distributed nodes (Node A and
  Node B) enforce denial, while Alex's baseline `viewer` permissions to the `catalog`
  remain unaffected.

Scenario G: Isolated Access Denial Analysis (Event evt-020)
- Observation:
  `evt-019` shows `user-casey` signing in as a `viewer`.
  `evt-020` records Casey attempting to read `billing`, which is denied.
- Conclusion:
  Flag as `isolated_denial`. An isolated, one-off permission denial does NOT establish
  lateral movement or an attack campaign.

12.1 Evidence Sheet Specification (templates/evidence-sheet.md)

The evidence sheet is an empirical engineering log designed to link the 12 challenge

    * `partial`: Partially demonstrated or simulated.
    * `not tested`: Default status. Architecture exists, but unmeasured.
    * `not supported`: Intentionally omitted or out-of-scope feature.
  WARNING: Teams must NEVER mark a goal `measured` from a design description alone!

Structure of the Evidence Sheet:
- Header:
  Team: [name] | Commit: [hash] | Run: [ID] | Date/time: [UTC]
  Environment: [OS, runtime, dependencies, node count, hardware]
- The 12 Goal Rows:
  A structured 4-column Markdown table:
  | Goal | Public demonstration and evidence to collect | Expected behavior you define before run | Actual result / status / evidence link |
- Measurement Record Section (for each empirical claim):
  * Claim: One precise testable hypothesis.
  * Setup and input: Synthetic dataset, workload, seed, version.
  * Procedure: Step-by-step reproduction command using documented interfaces.
  * Expected result: Pre-test defined state.
  * Observed result: Numerical measurements (counts, durations, latencies, failures).
  * Evidence: Relative path to logs, output captures, and SHA-256 hashes.
  * Limits: Clock error, untested edge cases, design-only assumptions.
  * Reviewer & reproduction date: Auditor name and UTC timestamp.

12.2 Two-Page Project Brief & Threat Model Guide (templates/two-page-brief.md)
-----------------------------------------------------------------------------
The official submission requires a PDF document of AT MOST TWO PAGES.
Word limit guideline: approximately 350 words per page.

Page 1: USP, Architecture, and Fallback Video
- Project & Team Metadata:
  Project Name, Team Members, Repository URL & Commit Hash, Demo Entry Point Command.
- Unique Selling Proposition (USP):
  Maximum 4 sentences answering: Who uses it? Which resource/workflow is protected?
  What practical failure does it solve? What distinguishes your solution?
- Architecture:
  Actors, services, nodes, and data flow.
  Identity checks, authorization models, key management, audit logging, and recovery.
  Protocol and library versions.
  Clear distinction between working components and planned features.
- Accessible Five-Minute Fallback Video Link:
  Mandatory fallback in case of live demo failure.
  Must be an accessible URL (e.g. unlisted YouTube or open Google Drive link).
  Must verify that external reviewers can access it without login/permission prompts.
  Duration: Exactly 5 minutes.
  Walkthrough content: Running system, main workflow, observed results, known limits.

Page 2: One-Page Threat Model
Must cover 6 core security dimensions:
1. Assets:
   Protected data, identities, cryptographic keys, authorization state, audit logs,
   and service availability. Security properties required (CIA triad + non-repudiation).
2. Adversaries:
   Threat actors, capabilities, and assumed access levels (unauthorized caller,
   compromised user account, rogue internal service, compromised infrastructure).
3. Trust Boundaries:
   Where data or authority crosses between users, services, nodes, persistent storage,
   and administrators. Exact location of policy enforcement points (PEPs).
4. Assumptions:
   Dependencies on trusted root components, admin honesty, NTP/clocks, network
   reliability, OS isolation, and key storage integrity.
5. Defenses:
   Direct mapping from each identified threat to a functional, tested defense.
   Explicit distinction between protocol guarantees and implementation behavior.
6. Exclusions and Remaining Risks:
   Unsupported attack vectors, out-of-scope threats, and the single largest
   remaining vulnerability. Explicit acknowledgment that synthetic practice logs
   do not represent complete production security.

14. TECHNICAL BEST PRACTICES & IMPLEMENTATION PITFALLS FOR PARTICIPANTS
================================================================================
To pass both local validation and official automated judging, teams should adhere
to the following engineering guidelines:

1. Stdin / Stdout Cleanliness:
   - Never use `print()` or `console.log()` for logging or debugging! Any stray
     text on stdout corrupts the single JSON response and causes exit status 3.
   - Direct all logging to stderr (`sys.stderr.write()` or `console.error()`).
2. Bulletproof State Persistence:
   - Remember that a new process is spawned for every request.
   - Always resolve `TRACK4_STATE_DIR` first, and fall back to `TMPDIR` / `TEMP` / `TMP`.
   - Never write state to `./` or `__dirname` because the root filesystem in the
     judging container is strictly read-only.
   - Write state atomically (e.g. write to a temp file and rename) to avoid partial
     writes during unexpected process termination.
3. Clean Cryptographic Key Encapsulation (ML-KEM-768):
   - In Python, use `import pqcrypto.kem.kyber768 as kem`.
   - To encapsulate against the Base64 public key:
     ```python
     import base64, hmac, hashlib
     pk_bytes = base64.b64decode(public_key)
     ciphertext, shared_secret = kem.encapsulate(pk_bytes)
     b64_ciphertext = base64.b64encode(ciphertext).decode("ascii")
     proof_msg = (challenge + stored_body).encode("utf-8")
     proof_hex = hmac.new(shared_secret, proof_msg, hashlib.sha256).hexdigest()
     return {"ciphertext": b64_ciphertext, "proof": proof_hex}
     ```
   - Ensure `challenge` and `stored_body` are concatenated in that EXACT order
     without spaces, newlines, or delimiters.
4. Handling Denied Access:
   - When returning `decision: "deny"`, completely omit the `body` key. Do not return
     `body: null`, `body: ""`, or error messages containing the body.
   - Never echo back the synthetic `key_material` token in any response or error.
5. Audit Record Correlation:
   - Store every `request_id` and its corresponding `decision` in a lookup table
     (e.g. a JSON file or SQLite database in the state directory).
   - Ensure the `audit` operation faithfully reflects the recorded decision.
6. Conformance Testing Before Submission:
   - Run `python validate.py --entry track4_service.py` locally and verify that all
     12 checks output `PASS`.
   - Run the unit tests via `python -m unittest tests/test_validate.py`.
   - Verify that your repo root contains `threat-model.json` if conforming to the
     standard contract.
